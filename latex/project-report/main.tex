\chapter{项目概述}
\section{建设背景}
反洗钱系统需要在客户主数据、账户关系和交易流水的基础上识别异常行为，并将监控结果转化为可调查、可复核、可审计的业务记录。本项目实现了一套完整的 AML 基础工作流：交易数据进入平台后，由规则引擎按时间窗口统计并生成命中，命中进一步形成预警，分析人员可将预警升级为案件并完成调查闭环。

系统同时提供名单筛查、风险评分、统计仪表盘、CSV 报表与审计查询，并通过适配器隔离 AMLSim、Apache Fineract 和 OpenSanctions/Yente 等外部系统。外部服务不可用时，核心业务仍可独立运行。

\section{建设目标}
\begin{enumerate}
\item 形成客户、账户和交易的统一数据基础，并保证关键关系和来源可追溯。
\item 使用版本化规则执行大额、高频和累计交易监控，记录执行批次与规则命中。
\item 建立预警审核、案件分派、调查笔记、证据管理、状态流转和关闭机制。
\item 对真实外部数据与模拟数据进行显式区分，避免测试结果被误认为真实合规结论。
\item 通过权限、参数校验、审计日志和数据库约束保障关键操作的完整性。
\item 提供可重复部署、可自动测试、可从源码追溯的工程化交付物。
\end{enumerate}

\chapter{需求分析}
\section{业务角色}
系统以 RBAC 模型控制访问。当前数据库初始化包含管理员、合规分析、案件调查、审计和只读类角色，并通过权限关联表分配客户读取、交易导入、规则执行、预警审核、案件调查、筛查执行、报表读取和审计读取等权限。前端根据权限隐藏不可用菜单，后端方法级鉴权是最终安全边界。

\section{非功能需求}
数据库结构仅由 Flyway 演进，金额使用高精度数值，时间以 UTC 持久化；写操作记录审计，状态变更遵循状态机；外部 HTTP 调用具备超时和明确失败处理；敏感配置来自环境变量；生产环境不得使用开发默认凭据。当前实现为单机容器化部署，不包含高可用、集中日志、生产密钥托管和自动灾备。

\section{模块划分}
后端源码位于 \code{backend/src/main/java/com/example/aml}。\code{auth/security/user} 负责认证授权；\code{customer/account/transaction} 负责基础数据；\code{rule/alert/casework} 构成监控处置主链路；\code{screening/risk} 负责名单筛查和风险评分；\code{dashboard/audit} 提供统计、报表和审计；\code{integration} 隔离外部系统协议。

\section{关键设计原则}
\begin{itemize}
\item 采用模块化单体，降低部署复杂度，同时保持领域边界清晰。
\item 规则参数采用受控模板和白名单，不执行用户提交的任意 DRL。
\item 规则命中键和预警关联使用唯一约束实现数据库级幂等。
\item 真实、模拟和混合数据来源沿筛查与评分结果传播。
\item 案件证据逻辑删除，历史和审计记录不做业务物理删除。
\end{itemize}

\chapter{核心业务设计}
\section{客户、账户与交易}
客户是平台的主体对象，账户通过关联表与客户建立关系，交易归属于账户。KYC 在客户页保存脱敏资料摘要，经过待审核、通过或退回；通过记录到期后允许重新提交，当前状态与历史可追溯，审核结论不自动修改客户风险等级。平台及 AMLSim CSV 使用 UTF-8 流式解析，支持可选 BOM、引号、字段内逗号及换行、转义双引号和空字段。导入最多积累 100 条有效记录后独立提交，坏记录保留定位和错误计数，已提交块不会被后续坏记录整体回滚。\code{source + external_id} 唯一约束构成跨批次幂等边界；尚未实现断点续传或吞吐性能基准。

\section{规则执行与预警生成}
规则库保存定义、版本和参数。后端执行接口可传规则代码和 \code{asOf}，当前网页上的“执行规则检测”按钮则默认请求所有已启用的 R001--R003，未提供时间输入。R001 在数据库按金额阈值筛选，仍覆盖截至执行时刻的历史交易；R002/R003 分别使用配置的分钟/小时窗口查询，再构造 Drools 事实对象。命中保存参与交易并生成预警，重复命中键不会重复写入。运行状态在独立事务中保存，业务事务失败后可保留 FAILED、处理数和非敏感错误类别。
2026-10-23 的真实 PostgreSQL 浏览器测试曾发现三规则版本范围超过 \code{scope varchar(30)}，执行记录插入失败且无该次 FAILED 行。Flyway V7 将字段扩为 \code{varchar(160)}；本轮 PostgreSQL 回归与浏览器均验证默认启用 R001--R003 的执行成功及 R001 预警，不再依赖停用其他规则。阈值和业务判断未改。

\section{案件调查闭环}
预警升级案件在同一事务中建立案件与预警关系。案件支持调查员分派、笔记、证据文件元数据及 SHA-256、状态历史和关闭结论。状态依次为 OPEN、INVESTIGATING、PENDING\_REVIEW 和 CLOSED，复核阶段可退回调查；关闭后禁止继续分派、添加笔记和修改证据。

\chapter{数据设计}
\section{迁移策略}
数据库使用 PostgreSQL 16.10，结构由 Flyway V1--V7 管理，Hibernate 设置为 \code{ddl-auto=validate}。2026-10-15 的 V1--V6 历史空库迁移得到 34 张应用表；V7 新增 KYC 历史表、审核字段与权限，并扩展规则执行范围字段。本轮 Testcontainers 对 V1--V7 完整迁移和实体校验通过。金额字段使用 \code{numeric(19,4)}，时间字段使用 \code{timestamptz}，主要实体使用 UUID 主键。

\section{完整性与可追溯性}
外键保证客户、账户、交易、命中、预警和案件之间的引用完整性；业务唯一键防止重复导入和重复告警；风险历史与案件历史采用追加式记录；证据文件本体存储在独立卷，数据库保存路径、摘要和逻辑移除信息。系统没有实现审计日志签名或防篡改存储，该能力属于后续安全增强范围。

\chapter{接口与安全设计}
\section{接口概况}
2026-10-15 历史 OpenAPI 实测包含 48 个路径、53 个操作；本轮新增三条 KYC 操作，未重新统计当前总数。业务接口以 \code{/api} 为前缀，登录以外需要 Bearer JWT。客户 KYC 位于客户资源下；规则、预警、案件等接口清单及权限见 API 手册。

\section{安全控制}
\begin{itemize}
\item 密码使用 BCrypt 哈希，JWT 密钥和数据库凭据通过环境变量注入。
\item 关键入口使用权限表达式，前端菜单隐藏不作为安全边界。
\item DTO 使用 Jakarta Validation，业务服务再次校验状态、归属关系和状态机。
\item 外部服务禁用、超时、非 2xx 和坏响应均显式失败，不自动伪造成功结果。
\item CSV 输出对公式注入字符进行中和，证据文件计算 SHA-256。
\end{itemize}

\section{已知安全问题}
2026-10-15 历史基线中，错误密码路径的失败次数和失败审计与登录事务共同回滚，锁定未实际生效。现采用独立事务、行级锁和统一 401 响应；2026-10-30 的四项 PostgreSQL 测试已覆盖持久化、五次锁定、到期解锁、成功重置、未知用户统一响应与并发失败计数。生产部署仍需要 TLS、密钥托管、病毒扫描、集中日志、备份恢复和最小权限数据库账号。

\chapter{结论}
当前系统已经形成结构清晰、可运行、可测试的 AML 核心业务平台。其主要价值在于将基础主数据、交易监控、预警处置、案件调查、筛查评分、统计报表和审计记录连接为可追溯闭环，并以 Flyway、自动化测试、容器化部署和清晰的外部适配边界保证工程可维护性。系统仍存在明确的功能和安全边界，部署到真实业务环境前必须完成安全加固、真实外部系统联调和监管要求评估。
